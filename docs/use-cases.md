# ccpick のユースケースと機能

利用者が何をしたいか（ユースケース）を決め、CLI とサーバーのどちらで受け持つかを振り分け、ログイン後の機能を詰める。

## 構成

```
手元の CLI (ccpick) ──── ccpick サーバー（インスタンス）
                          ・公開インスタンス ccpick.dev（招待制）
                          ・Org が自分で立てるインスタンス（セルフホスト）
```

- **CLI が唯一の画面**。読む・選ぶ・理由を書く・書き込む・戻すを、すべてターミナルで行う。Web のフロントエンドは持たない
- **サーバーは 1 種類**。公開用も Org 用も同じコードを設定違いで動かす。Cloudflare Workers + D1 と、Node + SQLite（Docker）の両方で動かせるようにする
- CLI は複数のインスタンスを登録できる（`ccpick remote add team https://ccpick.example.internal`）。既定は公開インスタンス

## このドキュメントの範囲

**ログイン後の機能** を扱う。アカウント管理（登録、ログイン、SSO との接続、招待制、メンバーかどうかの判定）は別に作り、ここでは境界の約束だけを決める。

### アカウント管理との境界

サーバーの機能は、リクエストごとに認証層から次の情報を受け取るだけにする。SSO や招待の仕組みを直接呼ばない。

```ts
interface Principal {
  userId: string;   // インスタンスの中で変わらない ID（SSO の ID とは別に払い出す）
  handle: string;   // 表示名（投稿の作者として見える）
  roles: ("member" | "moderator" | "admin")[];
}
```

- 認証層はリクエストを受けて `Principal` を作るか、401 を返す。機能側は `Principal` があれば動く
- CLI は `ccpick login [remote]` でインスタンスのログイン手順を始め、受け取ったトークンを `~/.ccpick/` にインスタンスごとに保存する（本人だけが読める権限）。手順の中身はアカウント管理側が決める
- 開発とテストでは、固定のユーザーを返す仮の認証層を使う。本番の設定では起動しないようにする
- 招待制と段階的な解放もアカウント管理側で作る。そのための判断材料（匿名メトリクスの集計）は機能側が提供する（「運営向けの集計」）

## 登場人物

- **もらう人**：他人の設定から欲しいキーだけを自分の settings.json に入れたい
- **公開する人**：自分の設定を、理由を添えて他人に見せたい。役に立ったかを知りたい
- **モデレーター**：通報を処理する。Org では公開前の投稿を承認する
- **運営（admin）**：インスタンスの設定を決める。メトリクスを見て公開の広げ方を決める

## 振り分けの原則

| 原則 | 理由 |
|---|---|
| 手元のファイルを読む・書く・戻すのは CLI だけ | 貼り付けや受け渡しが要らない。秘密が手元から出る経路を作らない |
| 自分向けの並べ替えと比較は CLI でやる | 「自分に足りない順」は手元の settings.json と比べて CLI が並べる。自分の設定はサーバーに送らない |
| サーバーは保存・検索・集計 | 投稿の中身を見て「あなたにはこれ」と決めるのは CLI |
| マスクは CLI で行い、サーバーでもう一度検査する | サーバーは core の `verifyMasked` で、秘密らしい値の残った投稿を拒否する |
| 書き込み前の最終確認は省略しない | high の項目、値が置き換わる項目、マスク値の入力は、取り込む直前に必ず確認する |
| 終わりを見せる | 一件ずつ出す画面（pick、publish、feed、承認、通報の処理）は、件数を出して最後に止まる。無限には流さない |
| メトリクスは匿名で、設定の中身を入れない | 送るのは操作の回数と、投稿に出てくるキーについての情報だけ。アカウントとは結びつけない |

## 機能の詳細

### もらう：`ccpick pick`

```
$ ccpick pick kenta/python
  Python データ分析で事故らない設定 — kenta  #python #data #safety  (v3)
  自分の settings.json と比べました：持っていない 9、値が違う 2、同じ 4（飛ばします）

  ── 3 / 11 ───────────────────────────────────────────────
  あなたの設定になく、作者が理由を書いています

    「一度ビルド成果物ごと消されてから入れている。
      git 管理外のファイルは戻せないので」

  low  permissions.deny  Bash(rm -rf *)
  このインスタンスの 94% が採用（参加 18 環境中 17）

  あなたの settings.json にはありません。もらうと追加されます。

  [y] もらう  [n] もらわない  [l] あとで  [z] ひとつ戻す  [?] 詳しく
```

- **並び順**：①作者の理由があり、自分にない ②自分になく、採用率が高い ③自分にない ④値が違う（置き換えになるので後ろ）。あとでに回したものは最後。同じものは出さない
- **詳しく**（`?`）：スキーマの説明、リスクの理由、参照しているスクリプト、全文の値
- **終わり**：「もらう 4 件（high 1、置き換え 1）、もらわない 7 件」→ high と置き換えだけ全文で確認 → マスク値を入力または飛ばす → 書き込み →「取り込み 01H… として記録しました。`ccpick undo 01H…` で戻せます」
- **2 回目以降**：同じ投稿を前に pick していれば、前回決めたキーは出さず、増えた・変わったキーだけを出す（`--all` で全部）。前回もらわなかったキーをもう一度聞かない
- **履歴**：取り込みごとに、投稿 ID・版・もらったキー・もらわなかったキーを記録する（`~/.ccpick/`）。U5・U8 の材料になる
- 端末でないとき（パイプや CI）は対話せず、`--only` か `--yes-low`（low だけ入れる）を求める

### 公開する：`ccpick publish`

```
$ ccpick publish --to team
  ~/.claude/settings.json を読みました：22 項目
  マスク：値 4 件、パス 2 件を ~ に置換、確認してほしい箇所 2 件

  ── 1 / 22 ───────────────────────────────────────────────
  マスクした値を含みます

  medium  env  GITHUB_TOKEN = <<MASKED:env.GITHUB_TOKEN>>
  取り込む人は自分の値を入力するか、この項目を飛ばします。

  なぜこう設定したか（投稿に載ります。空でも可）:
  > _

  [y] 公開する  [n] 公開しない  [l] あとで  [e] 理由を $EDITOR で書く
```

- **並び順**：マスクした値 → high → 確認してほしい箇所 → medium → low
- **終わり**：タイトル・タグ・OS を入力 → 公開する内容を全文で表示 → マスク漏れを再検査 → 送信 → 投稿の参照（`team:kenta/python`）を表示。承認が要るインスタンスでは「承認待ち」と出す
- **更新（`--update`）**：前回の選択と理由を引き継ぐ。前回から増えたキー、値が変わったキー、なくなったキーだけを聞く。送ると新しい版になる
- 理由が 1 件もないときは「理由のある項目は、もらう人の画面で先に出ます」と一度だけ案内する（強制はしない）

### 投稿の版

- 投稿は更新のたびに版が上がる（v1, v2, …）。古い版も残し、取り込みの履歴はどの版から来たかを指す
- 項目 ID は値に基づくので、版をまたいでも同じキー・同じ値なら同じ ID になる。「増えた・変わった・なくなった」は ID の比較で出せる
- 投稿を消すと全版を消す。取り込み済みの人の settings.json と履歴には影響しない

### フォローとフィード：`ccpick feed`

```
$ ccpick feed
  前回から 5 件（フォロー中 3、あなたが取り込んだ投稿の更新 2）

  ── 1 / 5 ─────────────────────────────────────────────────
  更新  kenta/python  v2 → v3   あなたが前に取り込んだ投稿です
        増えたキー 2（理由つき 1）、変わったキー 1
  [p] 差分を pick  [s] 読む  [n] 次へ  [l] あとで  [u] この人のフォローをやめる
```

- 出すのは「前回 feed を見てから」の新着と更新だけ。最後まで見ると「新しいものはありません」で止まる
- 並び順は、自分が取り込んだ投稿の更新 → フォロー中の人の新着 → フォロー中のタグの新着。各グループの中では、自分に足りないキーが多い順（CLI が手元で並べる）
- 「いいね」は作らない。反応は「取り込まれた」「見送られた」「戻された」で足りる

### 作者への反応：`ccpick posts`

```
$ ccpick posts kenta/python
  Python データ分析で事故らない設定  v3  取り込んだ環境 41
                                     もらった  見送り  戻した
  permissions.deny  Bash(rm -rf *)       38       2       0
  hooks.PostToolUse ruff format …         12      25       6   ← 戻されやすい
  env               PYTHONDONTWRITEBYTECODE 3     30       0   ← 理由がありません
```

- 公開した人が「どのキーが役に立ったか」「理由を書き足すべきキーはどれか」を知るための画面
- 数は匿名メトリクスから集計する。誰が取り込んだかは出さない

### 採用状況：`ccpick stats`

```
$ ccpick stats --in team
  参加 18 環境（直近 30 日に送った環境）
  採用の多いキー
    permissions.deny  Bash(rm -rf *)          17/18  94%
    permissions.deny  Read(./.env)            15/18  83%
    env               BASH_DEFAULT_TIMEOUT_MS  9/18  50%  値が同じ 6
  入れたが戻されたキー
    hooks.PostToolUse prettier --write …    取り込み 8、戻した 5
  人気の投稿
    kenta/python      取り込んだ環境 11
```

- **採用**は「いま settings.json に入っているか」。戻したものは数えず、手で入れたものも数える
- **数える対象は、そのインスタンスの投稿に出てくるキーだけ**。送るのは、キーごとに「入っているか」「値が投稿と同じか」だけ。値そのもの、投稿にないキー、パスは送らない
- 参加は任意（`ccpick share adoption on`）。インスタンスの設定で既定を変えることはできない
- 匿名：環境 ID（手元で作るランダムな値、30 日ごとに作り直す）ごとに最新の状態だけを持ち、30 日送られなければ消す。作り直しの前後が重なるので数は概数になる。人数が少ないとき（5 環境未満）は割合を出さない
- 送るのは `pick` / `publish` / `feed` を使ったついでに 1 日 1 回まで

### モデレーション：`ccpick admin reports` / `review`

- 通報・承認待ちも、1 件ずつ出す画面で処理する。high の項目を全文で、マスク値と確認してほしい箇所を強調して見せる
- 通報の処理：[h] 非公開にする（作者に理由を伝える）[k] 問題なし [l] あとで
- 承認：[a] 承認 [r] 差し戻す（理由を書く）[l] あとで。差し戻された投稿は `ccpick posts` に理由つきで出て、`publish --update` で直して出し直す
- 承認が要るかはインスタンスの設定（Org 用は既定で必要、公開インスタンスは不要）

## 匿名メトリクス

### 送るもの

| イベント | 中身 |
|---|---|
| `pick` 完了 | 投稿 ID と版、もらったキー・見送ったキー（投稿に出てくるキーなので投稿を読める人には公開情報）、high の件数、あとでに回した件数 |
| `apply` / `undo` / `revert` | どの投稿のどの版から来た取り込みか、戻したキー |
| `publish` | 投稿 ID と版、項目数、理由つきの件数（理由の文章は送らない。投稿そのものには載る） |
| `search` / `feed` | 条件、結果の件数、pick に進んだか |
| 採用状況（参加した人だけ） | 投稿に出てくるキーごとの「入っているか・値が同じか」 |
| 共通 | CLI のバージョン、OS の種類、環境 ID |

### 送らないもの

- 手元の settings.json の値、投稿に出てこないキー、パス、マスク値、環境変数
- アカウント（メトリクスには認証ヘッダーを付けず、アカウントと結びつけない）。送り先は、その投稿があるインスタンスだけ
- サーバーは IP アドレスを保存しない

### 確かめる・止める

- 送る直前の中身を `ccpick telemetry show` でそのまま見られる
- `ccpick telemetry off` または `CCPICK_TELEMETRY=0` で止まる。止めても使える機能は変わらない
- 同意は、インスタンスに初めてログインしたときに取る

### 運営向けの集計（`ccpick admin metrics`）

公開の広げ方（招待の枠など、アカウント管理側の判断）に使う指標を出す。

| 観点 | 指標 |
|---|---|
| 健全性 | 投稿 100 件あたりの通報数、未処理の通報数、取り込み後 7 日以内に戻された割合 |
| 需給 | 投稿数と pick 数の比、検索で 0 件だった割合（タグ・キー別） |
| 活性 | 週ごとに pick / publish した環境の数 |
| 判断の質 | pick で high の項目が「もらう」になった割合 |

## サーバーの API（ログイン後の機能）

すべて `Principal` が要る。`/v1/metrics` だけは認証ヘッダーを付けずに受ける。

| メソッド | パス | 内容 |
|---|---|---|
| POST | `/v1/posts` | 投稿する（承認が要るインスタンスでは承認待ちになる） |
| GET | `/v1/posts/:id` | 取得（`?version=` で版を指定） |
| PUT | `/v1/posts/:id` | 更新（新しい版を作る）。作者のみ |
| DELETE | `/v1/posts/:id` | 全版を消す。作者のみ |
| GET | `/v1/posts?tag=&os=&key=&user=&q=&cursor=` | 検索 |
| GET | `/v1/feed?since=` | フォロー中の新着・更新 |
| PUT / DELETE | `/v1/follows/:kind/:name` | 人・タグのフォロー |
| GET | `/v1/me/posts` | 自分の投稿と反応の集計、差し戻しの理由 |
| GET | `/v1/stats/items?key=`、`/v1/stats/posts/:id` | 採用率、投稿ごとの反応 |
| POST | `/v1/metrics` | 匿名メトリクス |
| POST | `/v1/posts/:id/reports` | 通報 |
| GET / POST | `/v1/admin/reports`、`/v1/admin/reports/:id/resolve` | 通報の処理（moderator） |
| GET / POST | `/v1/admin/pending`、`/v1/admin/posts/:id/approve`、`…/reject` | 承認（moderator） |
| GET | `/v1/admin/metrics` | 運営向けの集計（admin） |

受け付けるときの検査：投稿形式として読めること、`verifyMasked` で秘密らしい値が残っていないこと、サイズ上限（例：64 KB）、ユーザーごとの回数制限。

## 既存の Web ローカル版

この構成では必須ではない。並び順・比較・進み具合の計算（`apps/web/src/model.ts`）は DOM に依存しない純粋関数なので、core に移して CLI の `pick` / `publish` から使う。

## マイルストーン（案）

| | 内容 |
|---|---|
| M1〜M3 | 済（core、CLI の apply / history / undo / revert / export、Web ローカル版） |
| M4 | CLI の対話：`pick`（比較・並び順・2 回目以降の差分・一発取り込み）と `publish`（選択・理由・更新）。投稿はファイルと URL で受け渡し |
| M5 | サーバー：投稿と版、検索、`show`、`remote`、通報と承認。認証は仮の認証層で動かす |
| M6 | メトリクスと集計：`posts` の反応、`stats`、`share adoption`、`telemetry`、`admin metrics` |
| M7 | フォローとフィード：`follow`、`feed`、`updates` |
| — | アカウント管理（SSO、招待制、段階的な解放）は別に進め、M5 以降の認証層と差し替える |

## 決めること

1. **Web ローカル版の扱い**：M4 で CLI に移したあと消すか。推し：消す（保守するものを減らす）
2. **ターミナルの対話の作り**：Node 標準の `readline` だけで作るか、ライブラリを入れるか。推し：`readline` で始める
3. **採用状況の既定**：インスタンスの設定で参加を既定にできるようにするか。推し：できないようにする。見せるかは本人が決める
4. **コメント・質問**：キーごとに「これは何のため？」と作者に聞ける機能を持つか。推し：最初は持たない（モデレーションの負担が増える）。理由が足りないキーは `posts` の「理由がありません」で作者に気づいてもらう
5. **古い版の保持**：全版を残すか、取り込まれていない版は消すか。推し：全版を残す（投稿は小さい）
6. **公開投稿の読み取り専用ページ**：`GET /p/:id` で HTML を返すページを出すか。推し：公開インスタンスを誰でも見られる段階に進めるときに出す
7. **集計を出す最小人数**：5 環境未満では割合を出さない、で足りるか。Org の小さいチームで個人が推測できないか
