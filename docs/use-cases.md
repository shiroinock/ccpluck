# ccpluck のユースケースと機能

利用者が何をしたいか（ユースケース）を決め、CLI と置き場所のどちらで受け持つかを振り分け、ログイン後の機能を詰める。

## 構成

```
手元の CLI (ccpluck) ──┬── GitHub バックエンド（先に作る）
                      │     社内の GitHub リポジトリを投稿の置き場所にする
                      │
                      └── サーバーバックエンド（後で作る）
                            社外に公開するとき。招待制、匿名メトリクス、採用状況
```

- **CLI が唯一の画面**。読む・選ぶ・理由を書く・書き込む・戻すを、すべてターミナルで行う。Web のフロントエンドは持たない
- **まず社内に展開する**。立てるものも運用するものもない GitHub バックエンドから始め、社外に公開するときにサーバーバックエンドを足す
- **コマンドと手元の処理は置き場所によらず同じ**。CLI の中に置き場所の差し替え口（`Backend`）を作り、`pick` / `publish` / `feed` などはそれだけを通して置き場所に触れる
- 置き場所は複数登録できる（`ccpluck remote add team github:example-org/claude-settings`）。投稿は `team:kenta/python` のように指す

## このドキュメントの範囲

**ログイン後の機能** を扱う。

- **GitHub バックエンド**：ログインと権限は GitHub のものをそのまま使う（社内の GitHub が SSO 連携済みならそれに乗る）。ccpluck 側でアカウントを管理しない
- **サーバーバックエンド**：アカウント管理（登録、SSO との接続、招待制）は別に作る。機能側は認証層から次の `Principal` を受け取るだけにする

```ts
interface Principal {
  userId: string;   // インスタンスの中で変わらない ID
  handle: string;   // 表示名（投稿の作者として見える）
  roles: ("member" | "moderator" | "admin")[];
}
```

## 登場人物

- **もらう人**：他人の設定から欲しいキーだけを自分の settings.json に入れたい
- **公開する人**：自分の設定を、理由を添えて他人に見せたい。役に立ったかを知りたい
- **モデレーター**：公開前の投稿をレビューする。通報を処理する（GitHub ではリポジトリの管理者・レビュアー）
- **運営**：置き場所の設定を決める（GitHub ではリポジトリの管理者）

## 振り分けの原則

| 原則 | 理由 |
|---|---|
| 手元のファイルを読む・書く・戻すのは CLI だけ | 貼り付けや受け渡しが要らない。秘密が手元から出る経路を作らない |
| 自分向けの並べ替えと比較は CLI でやる | 「自分に足りない順」は手元の settings.json と比べて CLI が並べる。自分の設定は置き場所に送らない |
| 置き場所にできることは置き場所に任せる | GitHub なら、版は git の履歴、承認は PR のレビュー、通報は Issue、権限はリポジトリの権限。ccpluck で作り直さない |
| マスクは CLI で行い、置き場所でもう一度検査する | GitHub では PR のチェック（Actions）で、サーバーでは受け付け時に、core の `verifyMasked` をかける。秘密が履歴に残ると消せないので、社内でもマスクする |
| 書き込み前の最終確認は省略しない | high の項目、値が置き換わる項目、マスク値の入力は、取り込む直前に必ず確認する |
| 終わりを見せる | 1 件ずつ出す画面（pick、publish、feed、レビュー、通報の処理）は件数を出し、最後に止まる。無限には流さない |
| 個人の状況は GitHub に置かない | 誰がどのキーを入れているか、何を取り込み・戻したかは手元（`~/.ccpluck/`）にだけ持つ。GitHub ではコミットに名前が残り、消せないため。採用状況と反応は、匿名で集計できるサーバーバックエンドで扱う |

## 置き場所ごとの実現方法

| 機能 | GitHub バックエンド | サーバーバックエンド（後で） |
|---|---|---|
| ログイン・権限 | GitHub（`gh` のログイン、または `GITHUB_TOKEN`） | アカウント管理側（`Principal`） |
| 投稿の保存 | `posts/<GitHub のログイン名>/<名前>.json` | DB |
| 投稿の版 | 投稿ファイルのコミット | 版番号 |
| 公開 | ブランチを切って PR を作る | API に送る |
| 承認 | PR のレビュー（ブランチ保護で必須にできる） | 承認待ちの状態 |
| マスク漏れの検査 | PR のチェック（`remote init` が Actions を用意） | 受け付け時 |
| 検索・取得 | 手元の clone（`~/.ccpluck/remotes/<名前>/`）を CLI が読む | API |
| フィード | 前回 sync してからの `git log` | API |
| フォロー | 手元に保存（`~/.ccpluck/follows.json`） | サーバーに保存 |
| 通報 | Issue（ラベル `ccpluck-report`） | API |
| 反応・採用状況 | 持たない（個人の状況を GitHub に置かないため） | 匿名メトリクスから集計 |
| 運営向けの集計 | なし（社内展開の段階では要らない） | 匿名メトリクスから集計 |

## 機能の詳細

### もらう：`ccpluck pick`

```
$ ccpluck pick team:kenta/python
  Python データ分析で事故らない設定 — kenta  #python #data #safety  (3f2a91c, 11/12)
  自分の settings.json と比べました：持っていない 9、値が違う 2、同じ 4（飛ばします）

  ── 3 / 11 ───────────────────────────────────────────────
  あなたの設定になく、作者が理由を書いています

    「一度ビルド成果物ごと消されてから入れている。
      git 管理外のファイルは戻せないので」

  low  permissions.deny  Bash(rm -rf *)

  あなたの settings.json にはありません。もらうと追加されます。

  [y] もらう  [n] もらわない  [l] あとで  [z] ひとつ戻す  [?] 詳しく
```

- **並び順**：①作者の理由があり、自分にない ②自分にない ③その他 ④値が違う（置き換えになるので後ろ）。あとでに回したものは最後。同じものは出さない。サーバーバックエンドでは、②の中を採用率の高い順にし、カードに「94% が採用」を出す
- **詳しく**（`?`）：スキーマの説明、リスクの理由、参照しているスクリプト、全文の値
- **終わり**：「もらう 4 件（high 1、置き換え 1）、もらわない 7 件」→ high と置き換えだけ全文で確認 → マスク値を入力または飛ばす → 書き込み →「取り込み 01H… として記録しました。`ccpluck undo 01H…` で戻せます」
- **2 回目以降**：同じ投稿を前に pick していれば、前回決めたキーは出さず、増えた・変わったキーだけを出す（`--all` で全部）。前回もらわなかったキーをもう一度聞かない
- **履歴**：取り込みごとに、置き場所・投稿・版（コミット）・もらったキー・もらわなかったキーを記録する（`~/.ccpluck/`。手元だけ）。`updates` と差分 pick の材料になる
- 端末でないとき（パイプや CI）は対話せず、`--only` か `--yes-low`（low だけ入れる）を求める

### 公開する：`ccpluck publish`

```
$ ccpluck publish --to team
  ~/.claude/settings.json を読みました：22 項目
  マスク：値 4 件、パス 2 件を ~ に置換、確認してほしい箇所 2 件

  ── 1 / 22 ───────────────────────────────────────────────
  マスクした値を含みます

  medium  env  GITHUB_TOKEN = <<MASKED:env.GITHUB_TOKEN>>
  取り込む人は自分の値を入力するか、この項目を飛ばします。

  なぜこう設定したか（投稿に載ります。空でも可）:
  > _

  [y] 公開する  [n] 公開しない  [l] あとで  [e] 理由を $EDITOR で書く
```

- **並び順**：マスクした値 → high → 確認してほしい箇所 → medium → low
- **終わり**：タイトル・タグ・OS を入力 → 公開する内容を全文で表示 → マスク漏れを再検査 → 送る
- **GitHub では**：手元の clone でブランチを切り、`posts/<ログイン名>/<名前>.json` をコミットして push し、PR を作る。「レビュー待ちです：<PR の URL>」と出す。レビューが要らない設定のリポジトリでは、チェックが通ると自動でマージされる
- **更新（`--update`）**：前回の選択と理由を引き継ぐ。前回から増えたキー、値が変わったキー、なくなったキーだけを聞く。送ると新しい版になる
- 理由が 1 件もないときは「理由のある項目は、もらう人の画面で先に出ます」と一度だけ案内する（強制はしない）

### 投稿の版

- GitHub では投稿ファイルのコミットが版になる。表示は短いコミット ID と日付（`3f2a91c, 11/12`）
- 項目 ID は値に基づくので、版をまたいでも同じキー・同じ値なら同じ ID になる。「増えた・変わった・なくなった」は ID の比較で出せる
- 投稿を消すとファイルを消す PR になる。履歴には残る（git の性質）。取り込み済みの人の settings.json と手元の履歴には影響しない

### フォローとフィード：`ccpluck feed`

```
$ ccpluck feed
  前回から 5 件（あなたが取り込んだ投稿の更新 2、フォロー中 3）

  ── 1 / 5 ─────────────────────────────────────────────────
  更新  team:kenta/python  9c01d2e → 3f2a91c   あなたが前に取り込んだ投稿です
        増えたキー 2（理由つき 1）、変わったキー 1
  [p] 差分を pick  [s] 読む  [n] 次へ  [l] あとで  [u] この人のフォローをやめる
```

- 出すのは「前回 feed を見てから」の新着と更新だけ。最後まで見ると「新しいものはありません」で止まる
- 並び順は、自分が取り込んだ投稿の更新 → フォロー中の人の新着 → フォロー中のタグの新着。各グループの中では、自分に足りないキーが多い順（CLI が手元で並べる）
- 「いいね」は作らない。反応は「取り込まれた」「見送られた」「戻された」で足りる
- GitHub では、`remote sync` で取ってきたコミットのうち、前回 feed を見た位置より後のものを読む

### 自分の投稿：`ccpluck posts`

```
$ ccpluck posts
  team:kenta/python   Python データ分析で事故らない設定  3f2a91c  公開済み
  team:kenta/rust     Rust と CI の待ち時間対策             —       レビュー待ち（PR #42）
  team:kenta/minimal  最小限：deny だけ入れる派             —       差し戻し「hook の用途を書いてください」
```

- 状態（レビュー待ち・差し戻し・公開済み）を出す。差し戻しなら PR のコメントを見せ、`publish --update` で直して出し直す
- GitHub バックエンドでは反応（取り込まれた数・戻された数）は出さない。サーバーバックエンドでは、キーごとの「もらった・見送り・戻した」を匿名の集計から出す。「戻されやすい」「理由がありません」を見て、作者が理由を書き足すきっかけにする

### 採用状況と反応（サーバーバックエンドのみ）

- **採用**は「いま settings.json に入っているか」。戻したものは数えず、手で入れたものも数える
- **送るのは、そのインスタンスの投稿に出てくるキーだけ**。キーごとに「入っているか」「値が投稿と同じか」と、手元の履歴から「どの投稿から取り込んだか・もらった／見送った／戻した」。値そのもの、投稿にないキー、パスは送らない
- 匿名メトリクスとして送り、アカウントとは結びつけない（「サーバーバックエンド」の節）。表示は割合と人数だけで、少人数（例：5 環境未満）では割合を出さない
- `ccpluck stats` で採用の多いキー、入れたが戻されたキー、人気の投稿を見る。`pick` / `show` のカードに採用率を出す

### モデレーション：`ccpluck admin review` / `reports`

- レビューと通報の処理も、1 件ずつ出す画面で行う。high の項目を全文で、マスク値と確認してほしい箇所を強調して見せる
- **レビュー**（GitHub では PR）：[a] 承認 [r] 差し戻す（理由を書く）[l] あとで。承認・差し戻しは PR のレビューとして記録する
- **通報**（GitHub では Issue）：[t] 取り下げる（投稿を消す PR を作り、Issue に理由を書く）[k] 問題なし（Issue を閉じる）[l] あとで
- 誰がレビューできるかは、GitHub ではリポジトリの権限とブランチ保護で決まる

## GitHub バックエンドの中身

```
ccpluck.json                    # 置き場所の設定（表示名、レビュー必須か、警告しないホスト）
posts/<ログイン名>/<名前>.json # 投稿（ccpluck-post 形式。サーバーバックエンドと同じ）
.github/workflows/ccpluck.yml   # PR のチェック：投稿として読めるか、マスク漏れ、自分のディレクトリだけを変えているか
.github/ISSUE_TEMPLATE/ccpluck-report.yml  # 通報用
```

個人の状況（採用状況、取り込み・戻しの履歴）はリポジトリに置かない。

- `ccpluck remote init` がこれらを用意する PR を作る
- CLI は `git` で clone / fetch / push し、PR・レビュー・Issue は GitHub の API を使う。トークンは `gh auth token` から取り、なければ環境変数 `GITHUB_TOKEN` を使う
- GitHub Enterprise Server にも対応する（`ccpluck remote add team github:example-org/claude-settings --host github.example.internal`）
- CLI の中ではこの処理を `Backend` の実装の 1 つとして閉じ込め、サーバーバックエンドと差し替えられるようにする

### ブランチ戦略

```
main                                    公開済みの投稿
 ├─ ccpluck/publish/<ログイン名>/<名前>    投稿・更新の PR（1 投稿 1 本）
 ├─ ccpluck/unpublish/<ログイン名>/<名前>  取り下げの PR
 └─ ccpluck/takedown/<ログイン名>/<名前>   モデレーターによる取り下げの PR（通報の Issue にひもづけ）
```

- **main**：PR でだけ変える。直接 push、force push、履歴の書き換えは禁止する（版はコミット ID で参照されるため）。マージは squash のみにし、1 回の publish が main の 1 コミットになるようにする
- **必須のチェック**：`remote init` が入れる Actions（投稿として読めるか、マスク漏れ、PR の作者が自分のディレクトリだけを変えているか）。レビューを必須にするかは `ccpluck.json` とブランチ保護で Org ごとに選び、必須でなければチェックが通ったら auto-merge する
- **publish 用ブランチ**：名前を投稿ごとに固定する。PR が開いていれば同じブランチに積んで PR を更新し、マージ済みなら最新の main から作り直して新しい PR にする。投稿は人ごとに別ファイルなので他人とは衝突しない。自分の同じ投稿を並行して更新したときは、手元の状態からファイルを作り直して自分のブランチに force push する
- マージ後のブランチは自動で消す（リポジトリ設定）
- **秘密は push の前に止める**：一度 push した内容は、PR を閉じてもブランチを消しても GitHub に残る（PR の ref が残るため）。Actions のチェックは二段目で、本命は CLI が push の直前にかけるマスク漏れの検査
- **同じリポジトリのブランチを使う**：社内ではメンバーに書き込み権限を渡す。読み取り権限だけの人が多い Org のための fork からの PR は、需要が出てから対応する
- **手元の clone は main だけを追う**。作業ブランチは publish のたびに作って push し、手元には残さない。フィードと `updates` の「前回どこまで見たか」は main のコミット ID で記録する

## 手元の履歴を git に載せ替える（後の改善）

今の取り込み履歴（`~/.ccpluck/imports/<ID>.json`）を、手元の git リポジトリ（`~/.ccpluck/history/`）のコミットとして積む形に置き換える。M5 で git を扱う部品を作った後に入れる。

| 今 | git で |
|---|---|
| `apply` / `pick` の 1 回の取り込み | 1 コミット。メッセージに投稿・版・項目を書く |
| `history` | `git log`（`git log -p` で差分も見られる） |
| `undo` | 打ち消すコミットを積む（履歴は消えない） |
| `revert <項目>` | その項目だけを戻すコミットを積む |
| 適用前の状態（undo のバイト一致） | 1 つ前のコミットの settings.json |

- **戻し方は ccpluck が計算する**：`git revert` は行単位なので、JSON ではカンマや並びの都合で衝突しやすい。何を戻すかは今どおり項目単位で ccpluck が決め、その結果を新しいコミットとして積む。git は記録の置き場所として使う
- **`~/.claude` を git 管理にしない**：認証情報などが入っているため。`~/.ccpluck/history/` に settings.json の写しを置いて記録し、本物への書き込みは今までどおり ccpluck が行う
- **手で編集した分も記録する**：取り込みの前に settings.json が前回の記録と違っていれば、先に「手で変更」のコミットを積む
- このリポジトリを自分の private リポジトリに push すれば、バックアップや別のマシンとの同期にも使える（任意。共有用のリポジトリとは別）

## サーバーバックエンド（後で作る）

社外に公開するときに作る。ここまでの機能を同じコマンドで使えるようにしたうえで、次を足す。

- **招待制と段階的な解放**：アカウント管理側で作る。判断材料として運営向けの集計（`ccpluck admin metrics`）を機能側が出す
- **採用状況と反応**：`stats`、`posts` の反応、`pick` / `show` の採用率（「採用状況と反応」の節）
- **匿名メトリクス**：採用状況と反応を、名前を残さずに集計する。環境 ID（手元で作るランダムな値、30 日ごとに作り直す）で数え、アカウントとは結びつけない。設定の値、投稿にないキー、パス、マスク値は送らない。`ccpluck telemetry show / off` で確かめ・止められる
- **運営向けの集計**：通報率、取り込み後に戻された割合、投稿数と pick 数の比、検索で 0 件だった割合、週ごとの利用環境数
- API の形は、GitHub バックエンドで社内の使われ方を見てから決める

## 既存の Web ローカル版

この構成では必須ではない。並び順・比較・進み具合の計算（`apps/web/src/model.ts`）は DOM に依存しない純粋関数なので、core に移して CLI の `pick` / `publish` から使う。

## 決めること

1. **Web ローカル版の扱い**：M4 で CLI に移したあと消すか。推し：消す（保守するものを減らす）
2. **ターミナルの対話の作り**：Node 標準の `readline` だけで作るか、ライブラリを入れるか。推し：`readline` で始める
3. **GitHub とのやりとり**：`gh` コマンドに頼るか、API を直接呼ぶか。推し：トークンだけ `gh` から借り、API は直接呼ぶ（`gh` がなくても `GITHUB_TOKEN` で動く）
4. **集計を出す最小人数**（サーバーバックエンド）：5 環境未満では割合を出さない、で足りるか。小さい Org のインスタンスで個人が推測できないか
5. **レビューを必須にするか**：`ccpluck.json` の既定を「レビュー必須」にし、ブランチ保護の設定は `remote init` で案内する（自動では変えない）
6. **キーごとの質問**：「これは何のため？」と作者に聞く機能。推し：GitHub では Issue で足りるので、`ccpluck ask <投稿> --key <キー>` で Issue を作るだけにする
