# ccpick のユースケースと機能

利用者が何をしたいか（ユースケース）を決め、CLI と置き場所のどちらで受け持つかを振り分け、ログイン後の機能を詰める。

## 構成

```
手元の CLI (ccpick) ──┬── GitHub バックエンド（先に作る）
                      │     社内の GitHub リポジトリを投稿の置き場所にする
                      │
                      └── サーバーバックエンド（後で作る）
                            社外に公開するとき。招待制、匿名メトリクス
```

- **CLI が唯一の画面**。読む・選ぶ・理由を書く・書き込む・戻すを、すべてターミナルで行う。Web のフロントエンドは持たない
- **まず社内に展開する**。立てるものも運用するものもない GitHub バックエンドから始め、社外に公開するときにサーバーバックエンドを足す
- **コマンドと手元の処理は置き場所によらず同じ**。CLI の中に置き場所の差し替え口（`Backend`）を作り、`pick` / `publish` / `feed` などはそれだけを通して置き場所に触れる
- 置き場所は複数登録できる（`ccpick remote add team github:example-org/claude-settings`）。投稿は `team:kenta/python` のように指す

## このドキュメントの範囲

**ログイン後の機能** を扱う。

- **GitHub バックエンド**：ログインと権限は GitHub のものをそのまま使う（社内の GitHub が SSO 連携済みならそれに乗る）。ccpick 側でアカウントを管理しない
- **サーバーバックエンド**：アカウント管理（登録、SSO との接続、招待制）は別に作る。機能側は認証層から次の `Principal` を受け取るだけにする

```ts
interface Principal {
  userId: string;   // インスタンスの中で変わらない ID
  handle: string;   // 表示名（投稿の作者として見える）
  roles: ("member" | "moderator" | "admin")[];
}
```

## 登場人物

- **もらう人**：他人の設定から欲しいキーだけを自分の settings.json に入れたい
- **公開する人**：自分の設定を、理由を添えて他人に見せたい。役に立ったかを知りたい
- **モデレーター**：公開前の投稿をレビューする。通報を処理する（GitHub ではリポジトリの管理者・レビュアー）
- **運営**：置き場所の設定を決める（GitHub ではリポジトリの管理者）

## 振り分けの原則

| 原則 | 理由 |
|---|---|
| 手元のファイルを読む・書く・戻すのは CLI だけ | 貼り付けや受け渡しが要らない。秘密が手元から出る経路を作らない |
| 自分向けの並べ替えと比較は CLI でやる | 「自分に足りない順」は手元の settings.json と比べて CLI が並べる。自分の設定は置き場所に送らない |
| 置き場所にできることは置き場所に任せる | GitHub なら、版は git の履歴、承認は PR のレビュー、通報は Issue、権限はリポジトリの権限。ccpick で作り直さない |
| マスクは CLI で行い、置き場所でもう一度検査する | GitHub では PR のチェック（Actions）で、サーバーでは受け付け時に、core の `verifyMasked` をかける。秘密が履歴に残ると消せないので、社内でもマスクする |
| 書き込み前の最終確認は省略しない | high の項目、値が置き換わる項目、マスク値の入力は、取り込む直前に必ず確認する |
| 終わりを見せる | 1 件ずつ出す画面（pick、publish、feed、レビュー、通報の処理）は件数を出し、最後に止まる。無限には流さない |
| 名前が残ることを隠さない | GitHub ではコミットに作者が残る。採用状況など個人の利用がわかる情報は、参加を任意にして、見えることを明示して同意を取る |

## 置き場所ごとの実現方法

| 機能 | GitHub バックエンド | サーバーバックエンド（後で） |
|---|---|---|
| ログイン・権限 | GitHub（`gh` のログイン、または `GITHUB_TOKEN`） | アカウント管理側（`Principal`） |
| 投稿の保存 | `posts/<GitHub のログイン名>/<名前>.json` | DB |
| 投稿の版 | 投稿ファイルのコミット | 版番号 |
| 公開 | ブランチを切って PR を作る | API に送る |
| 承認 | PR のレビュー（ブランチ保護で必須にできる） | 承認待ちの状態 |
| マスク漏れの検査 | PR のチェック（`remote init` が Actions を用意） | 受け付け時 |
| 検索・取得 | 手元の clone（`~/.ccpick/remotes/<名前>/`）を CLI が読む | API |
| フィード | 前回 sync してからの `git log` | API |
| フォロー | 手元に保存（`~/.ccpick/follows.json`） | サーバーに保存 |
| 通報 | Issue（ラベル `ccpick-report`） | API |
| 反応・採用状況 | 参加者が専用ブランチに名前つきで書く（任意） | 匿名メトリクスから集計 |
| 運営向けの集計 | なし（社内展開の段階では要らない） | 匿名メトリクスから集計 |

## 機能の詳細

### もらう：`ccpick pick`

```
$ ccpick pick team:kenta/python
  Python データ分析で事故らない設定 — kenta  #python #data #safety  (3f2a91c, 11/12)
  自分の settings.json と比べました：持っていない 9、値が違う 2、同じ 4（飛ばします）

  ── 3 / 11 ───────────────────────────────────────────────
  あなたの設定になく、作者が理由を書いています

    「一度ビルド成果物ごと消されてから入れている。
      git 管理外のファイルは戻せないので」

  low  permissions.deny  Bash(rm -rf *)
  参加者の 94% が採用（18 人中 17 人）

  あなたの settings.json にはありません。もらうと追加されます。

  [y] もらう  [n] もらわない  [l] あとで  [z] ひとつ戻す  [?] 詳しく
```

- **並び順**：①作者の理由があり、自分にない ②自分になく、採用率が高い ③自分にない ④値が違う（置き換えになるので後ろ）。あとでに回したものは最後。同じものは出さない
- **詳しく**（`?`）：スキーマの説明、リスクの理由、参照しているスクリプト、全文の値
- **終わり**：「もらう 4 件（high 1、置き換え 1）、もらわない 7 件」→ high と置き換えだけ全文で確認 → マスク値を入力または飛ばす → 書き込み →「取り込み 01H… として記録しました。`ccpick undo 01H…` で戻せます」
- **2 回目以降**：同じ投稿を前に pick していれば、前回決めたキーは出さず、増えた・変わったキーだけを出す（`--all` で全部）。前回もらわなかったキーをもう一度聞かない
- **履歴**：取り込みごとに、置き場所・投稿・版（コミット）・もらったキー・もらわなかったキーを記録する（`~/.ccpick/`）。`updates` と差分 pick の材料になる
- 端末でないとき（パイプや CI）は対話せず、`--only` か `--yes-low`（low だけ入れる）を求める

### 公開する：`ccpick publish`

```
$ ccpick publish --to team
  ~/.claude/settings.json を読みました：22 項目
  マスク：値 4 件、パス 2 件を ~ に置換、確認してほしい箇所 2 件

  ── 1 / 22 ───────────────────────────────────────────────
  マスクした値を含みます

  medium  env  GITHUB_TOKEN = <<MASKED:env.GITHUB_TOKEN>>
  取り込む人は自分の値を入力するか、この項目を飛ばします。

  なぜこう設定したか（投稿に載ります。空でも可）:
  > _

  [y] 公開する  [n] 公開しない  [l] あとで  [e] 理由を $EDITOR で書く
```

- **並び順**：マスクした値 → high → 確認してほしい箇所 → medium → low
- **終わり**：タイトル・タグ・OS を入力 → 公開する内容を全文で表示 → マスク漏れを再検査 → 送る
- **GitHub では**：手元の clone でブランチを切り、`posts/<ログイン名>/<名前>.json` をコミットして push し、PR を作る。「レビュー待ちです：<PR の URL>」と出す。レビューが要らない設定のリポジトリでは、チェックが通ると自動でマージされる
- **更新（`--update`）**：前回の選択と理由を引き継ぐ。前回から増えたキー、値が変わったキー、なくなったキーだけを聞く。送ると新しい版になる
- 理由が 1 件もないときは「理由のある項目は、もらう人の画面で先に出ます」と一度だけ案内する（強制はしない）

### 投稿の版

- GitHub では投稿ファイルのコミットが版になる。表示は短いコミット ID と日付（`3f2a91c, 11/12`）
- 項目 ID は値に基づくので、版をまたいでも同じキー・同じ値なら同じ ID になる。「増えた・変わった・なくなった」は ID の比較で出せる
- 投稿を消すとファイルを消す PR になる。履歴には残る（git の性質）。取り込み済みの人の settings.json と手元の履歴には影響しない

### フォローとフィード：`ccpick feed`

```
$ ccpick feed
  前回から 5 件（あなたが取り込んだ投稿の更新 2、フォロー中 3）

  ── 1 / 5 ─────────────────────────────────────────────────
  更新  team:kenta/python  9c01d2e → 3f2a91c   あなたが前に取り込んだ投稿です
        増えたキー 2（理由つき 1）、変わったキー 1
  [p] 差分を pick  [s] 読む  [n] 次へ  [l] あとで  [u] この人のフォローをやめる
```

- 出すのは「前回 feed を見てから」の新着と更新だけ。最後まで見ると「新しいものはありません」で止まる
- 並び順は、自分が取り込んだ投稿の更新 → フォロー中の人の新着 → フォロー中のタグの新着。各グループの中では、自分に足りないキーが多い順（CLI が手元で並べる）
- 「いいね」は作らない。反応は「取り込まれた」「見送られた」「戻された」で足りる
- GitHub では、`remote sync` で取ってきたコミットのうち、前回 feed を見た位置より後のものを読む

### 自分の投稿：`ccpick posts`

```
$ ccpick posts team:kenta/python
  Python データ分析で事故らない設定  3f2a91c  公開済み
  取り込んだ人 11（採用状況を共有している人のうち）
                                     もらった  見送り  戻した
  permissions.deny  Bash(rm -rf *)       10       1       0
  hooks.PostToolUse ruff format …         4       5       2   ← 戻されやすい
  env               PYTHONDONTWRITEBYTECODE 1       9       0   ← 理由がありません
```

- 状態（レビュー待ち・差し戻し・公開済み）を出す。差し戻しなら PR のコメントを見せ、`publish --update` で直して出し直す
- 反応は、採用状況を共有している人のぶんだけ数える（次の節）。数は出すが、誰かは出さない

### 採用状況と反応：`ccpick stats`

```
$ ccpick stats --in team
  採用状況を共有している人 18
  採用の多いキー
    permissions.deny  Bash(rm -rf *)          17/18  94%
    permissions.deny  Read(./.env)            15/18  83%
    env               BASH_DEFAULT_TIMEOUT_MS  9/18  50%  値が同じ 6
  入れたが戻されたキー
    hooks.PostToolUse prettier --write …    取り込み 8、戻した 5
  人気の投稿
    kenta/python      取り込んだ人 11
```

- **採用**は「いま settings.json に入っているか」。戻したものは数えず、手で入れたものも数える
- **共有するのは、その置き場所の投稿に出てくるキーだけ**。キーごとに「入っているか」「値が投稿と同じか」と、ccpick の履歴から「どの投稿から取り込んだか・もらった／見送った／戻した」。値そのもの、投稿にないキー、パスは共有しない
- **参加は任意**（`ccpick share adoption on --in team`）。置き場所の設定で既定を変えることはできない
- **GitHub では名前が残る**：参加した人は、専用ブランチ `ccpick/adoption` の `adoption/<ログイン名>.json` を更新する（`pick` / `publish` / `sync` のついで、1 日 1 回まで）。本流のブランチや PR は汚さない。リポジトリを読める人には誰が何を使っているかが分かるので、参加時に「リポジトリを読める人に、あなたがどの共有キーを使っているかが見えます」と明示して同意を取る
- **表示は割合と人数だけ**。名前の一覧は出さない。5 人未満のときは割合を出さない
- 集計は各自の CLI が手元の clone で行う
- 共有する直前の中身は `ccpick share adoption --show` でそのまま見られる。`off` でやめると自分のファイルを消す（履歴には残る）

### モデレーション：`ccpick admin review` / `reports`

- レビューと通報の処理も、1 件ずつ出す画面で行う。high の項目を全文で、マスク値と確認してほしい箇所を強調して見せる
- **レビュー**（GitHub では PR）：[a] 承認 [r] 差し戻す（理由を書く）[l] あとで。承認・差し戻しは PR のレビューとして記録する
- **通報**（GitHub では Issue）：[t] 取り下げる（投稿を消す PR を作り、Issue に理由を書く）[k] 問題なし（Issue を閉じる）[l] あとで
- 誰がレビューできるかは、GitHub ではリポジトリの権限とブランチ保護で決まる

## GitHub バックエンドの中身

```
ccpick.json                    # 置き場所の設定（表示名、レビュー必須か、警告しないホスト）
posts/<ログイン名>/<名前>.json # 投稿（ccpick-post 形式。サーバーバックエンドと同じ）
.github/workflows/ccpick.yml   # PR のチェック：投稿として読めるか、マスク漏れ、自分のディレクトリだけを変えているか
.github/ISSUE_TEMPLATE/ccpick-report.yml  # 通報用

# ブランチ ccpick/adoption（採用状況を共有する人のぶんだけ）
adoption/<ログイン名>.json
```

- `ccpick remote init` がこれらを用意する PR を作る
- CLI は `git` で clone / fetch / push し、PR・レビュー・Issue は GitHub の API を使う。トークンは `gh auth token` から取り、なければ環境変数 `GITHUB_TOKEN` を使う
- GitHub Enterprise Server にも対応する（`ccpick remote add team github:example-org/claude-settings --host github.example.internal`）
- CLI の中ではこの処理を `Backend` の実装の 1 つとして閉じ込め、サーバーバックエンドと差し替えられるようにする

## サーバーバックエンド（後で作る）

社外に公開するときに作る。ここまでの機能を同じコマンドで使えるようにしたうえで、次を足す。

- **招待制と段階的な解放**：アカウント管理側で作る。判断材料として運営向けの集計（`ccpick admin metrics`）を機能側が出す
- **匿名メトリクス**：採用状況と反応を、名前を残さずに集計する。環境 ID（手元で作るランダムな値、30 日ごとに作り直す）で数え、アカウントとは結びつけない。設定の値、投稿にないキー、パス、マスク値は送らない。`ccpick telemetry show / off` で確かめ・止められる
- **運営向けの集計**：通報率、取り込み後に戻された割合、投稿数と pick 数の比、検索で 0 件だった割合、週ごとの利用環境数
- API の形は、GitHub バックエンドで社内の使われ方を見てから決める

## 既存の Web ローカル版

この構成では必須ではない。並び順・比較・進み具合の計算（`apps/web/src/model.ts`）は DOM に依存しない純粋関数なので、core に移して CLI の `pick` / `publish` から使う。

| M4 | CLI の対話：`pick`（比較・並び順・2 回目以降の差分・一発取り込み）と `publish`（選択・理由・更新）。投稿はファイルと URL で受け渡し |
| M5 | GitHub バックエンド：`remote init / add / sync`、`publish --to`（PR）、`search`、`show`、`pick` の置き場所対応と版の記録、`updates` |
| M6 | フォローとフィード、モデレーション：`follow`、`feed`、`posts`、`report`、`admin review / reports` |
| M7 | 採用状況と反応：`share adoption`、`stats`、`posts` の反応、`pick` の採用率表示 |
| — | 社内で使われ方を見る |
| M8 | サーバーバックエンド：社外公開、招待制（アカウント管理側と合わせて）、匿名メトリクス、運営向けの集計 |

## 決めること

1. **Web ローカル版の扱い**：M4 で CLI に移したあと消すか。推し：消す（保守するものを減らす）
2. **ターミナルの対話の作り**：Node 標準の `readline` だけで作るか、ライブラリを入れるか。推し：`readline` で始める
3. **GitHub とのやりとり**：`gh` コマンドに頼るか、API を直接呼ぶか。推し：トークンだけ `gh` から借り、API は直接呼ぶ（`gh` がなくても `GITHUB_TOKEN` で動く）
4. **社内で名前つきの採用状況を許すか**：任意参加・明示の同意・割合と人数だけの表示、で受け入れられるか。だめなら M7 は入れず、サーバーバックエンドの匿名集計を待つ
5. **集計を出す最小人数**：5 人未満では割合を出さない、で足りるか。小さいチームで個人が推測できないか
6. **レビューを必須にするか**：`ccpick.json` の既定を「レビュー必須」にし、ブランチ保護の設定は `remote init` で案内する（自動では変えない）
7. **キーごとの質問**：「これは何のため？」と作者に聞く機能。推し：GitHub では Issue で足りるので、`ccpick ask <投稿> --key <キー>` で Issue を作るだけにする
